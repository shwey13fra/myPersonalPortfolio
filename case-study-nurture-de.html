The problem

I navigated German pregnancy bureaucracy as an expat. The information exists — it's fragmented across health, employment, benefits and insurer portals, mostly in German, and you can't search for a rule if you don't know the German word for it. The difficulty isn't that the information is missing. It's the gap between knowing a benefit exists and being able to act on it.

Then the finding that reframed the product:

I wrote 40 evaluation questions from my own experience before looking at what my corpus covered. Roughly half turned out to be things the system should refuse or simply doesn't have — finding an English-speaking gynaecologist, a practice that says it's full, comparing two hospitals. Every one is something I typed into a search bar at 2am, and none is a question an official portal is built to answer.

Why this matters: it's the product research most portfolio projects skip, because writing eval questions from your corpus is easier and produces better numbers.

What it does

DoesDoesn't

Computes Mutterschutz dates in PythonLet the model do date arithmetic

Reporting a rule versus making a determination. "Familienportal states the protection period begins six weeks before the expected date" is grounded retrieval. "Your protection period begins on 1 February" is an eligibility decision — deliberately out of scope.

Architecture

22 official sources → Question-anchored chunking → Multilingual embeddings + BM25 → Hybrid retrieval · RRF + metadata filter → Cross-encoder rerank → Grounded generation with citations → 56-case evaluation

The workflow is the more interesting half:

classify → profile check → retrieve ↻ → grade evidence → timeline → generate → verify citations
    │            │
 medical      missing
 refuse         ask

This is a workflow, not an autonomous agent. Two routing branches and one retry loop, hard-capped at 2. In a domain where a wrong answer means someone misses a benefit deadline, bounded and traceable beats flexible.

Selected findings

This is what separates the project from a tutorial. Each finding carries the number that makes it a measurement, not an anecdote.

rank 6 of 225 · recall@5 0.75 → 0.90

The answer was retrieved, then discarded

An English query returned "I don't have that information" while holding the answer. The correct German chunk was retrieved at rank 6 of 225 and cut by a top-4 window.

BEFORE                          AFTER (rerank pool 100)
0  EN  tk_maternity_pay         0  DE  fam_mutterschutz  ← the answer
1  EN  tk_maternity_pay         1  EN  tk_maternity_pay
2  EN  tk_maternity_benefits    2  DE  fam_mutterschutz
3  EN  tk_maternity_pay         3  EN  tk_maternity_benefits
─── top-4 cutoff ───
6  DE  fam_mutterschutz  ← discarded

recall@5 reports 0 whether a chunk was never found or found and thrown away. Those need completely different fixes — a new model versus a bigger number. Only the trace distinguishes them.

3 silent failures

Failures that don't crash

Three bugs produced plausible output rather than errors:

FailureWhat it looked like
Chunk retrieved at rank 6, cut by the windowA coverage gap
Filter vocabulary mismatch emptying the poolAn honest partial answer
A test overwriting the published deliverableA working page

A system that abstains gracefully is harder to debug than one that produces garbage, because the failure mode is indistinguishable from correct behaviour.

reranking retraction

A retraction

I reported that reranking added nothing on this corpus. Wrong — my eval harness fed it a 10-candidate pool while the correct chunks sat at ranks 20–27. It never saw them. An invalid measurement, not a weak component. A config comparison is only meaningful if each config gets a fair chance to work.

0.85 → 0.75 (real baseline)

A number I carried for weeks

I quoted a recall baseline of 0.85 across several phases. It was never sourced from a file. The real figure was 0.75 — my remembered number understated my own improvement. Caught because the tooling refused to publish a figure it couldn't trace to a file.

Fixed structurally: a test that fails the build if any number on the public page is hand-typed rather than read from data.

retrieval 86–89% · generation 5–10%

The latency inversion

Predicted generation would dominate query time. Measured: retrieval 86–89%, generation 5–10% — reranking 100 candidates on CPU was the entire cost. Right about the production topology, wrong about the machine.

Then I deployed, offloaded the reranker to a hosted endpoint, and generation became the bottleneck exactly where the original estimate said it would be. Latency is architecture plus hardware.

h2-only hierarchy

Structure that lives in a convention, not in markup

The German family portal marks everything as h2 — questions, sub-parts, side modules alike. The hierarchy is expressed as a convention: a question mark means a new topic. A generic splitter would have worked and quietly retrieved worse forever.

The same trait bit twice — half my corpus-derived eval questions accidentally restated the heading of the chunk they targeted, which would have inflated recall while measuring lexical overlap.

Honest limitations

  • Prototype scale — 22 sources, 225 chunks, 56 eval cases. Not 500 with inter-annotator agreement.
  • The real defect: recall@5 is 0.94 on German questions but ~0.30 on English questions about German-only topics. Cross-lingual answering works once the source is retrieved; cross-lingual retrieval still fails when English chunks crowd out a German-only source.
  • Freshness disclosure is implemented but untestable — the whole corpus was fetched on one day, so there's no date spread to exercise it.
  • Behaviour figures were measured on Opus; the live demo runs Sonnet for latency. Retrieval recall is model-independent so those numbers stand, but answer quality on Sonnet hasn't been re-evaluated.
  • No auth, no rate limiting, no multi-tenancy. Never operated a vector store under production load.
  • No fine-tuning. Deliberately — German benefit rules get amended, and a fine-tuned model bakes in stale law with no citation trail.
